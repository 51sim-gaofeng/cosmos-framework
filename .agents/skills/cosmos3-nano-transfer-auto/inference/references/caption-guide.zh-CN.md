<a id="av-per-view-caption"></a>
# 自动驾驶逐视角描述文本指南

为同一个物理场景编写逐相机描述文本（caption），每段正文只描述对应视角的内容。
以同步 WSM 帧作为物体布局与运动的依据。

<a id="options-and-defaults"></a>
## 选项与默认值

使用自然语言指定选项；无需记忆 CLI 标志。

| 选项 | 可选值 | 省略时的默认值 |
| --- | --- | --- |
| 格式 | 单段，或带时间戳的文本块 | 带时间戳的文本块 |
| 长度 | 短、长，或为每个视角明确指定词数范围 | 长：每个视角的所有文本块合计 300–400 个词（仅计正文） |
| 视角 | 全部提供的视角、仅前视，或指定名称的相机 | 全部提供的视角 |

示例：

- “对这些 WSM 控制和场景属性使用 av-per-view-caption。”
  使用上述默认值。
- “生成长篇、全视角、带时间戳的描述文本，每个视角 300–400 词。”
- “生成仅前视的段落描述文本，80–120 词。”
- “使用 av-per-view-caption：向我展示选项和默认值。”

对于选项／帮助请求，展示此表及示例，不要求提供媒体，也不启动描述文本编写。
对于生成请求，在检查媒体之前说明所选格式、长度和视角，包括采用的默认值。
不要仅为了使用默认值而要求单独确认。
除非用户指定其他范围，“长”表示每个视角 300–400 个正文词；
“短”是定性要求，除非提供了具体范围。
不要为了达到词数要求而堆砌内容或编造没有依据的描述。

段落式和带时间戳的描述文本均受支持。
原文指出，模型训练数据使用带时间戳的描述，且实验中这种格式的生成效果更好。
[参考场景的两种变体](../../shared/reference-scene.zh-CN.md#choose-a-caption-style)
展示了两种格式及其选择方式。
后训练也优先使用带时间戳的描述文本，并遵循
[以目标为依据的训练工作流](../../post-training/references/data-contract.zh-CN.md#training-captions)。

编写前，完整阅读[描述文本策略](#caption-policy)一节。
其中包含交通、外观、四项属性和时间关系规则。

<a id="establish-the-scope"></a>
## 确定范围

为每个相机视角新建描述正文，或将已有文本扩写后另存。
保留与场景条件相容的明确外观设定；修正与 WSM 矛盾的交通叙述，并记录修改内容。
工作开始前，说明所选场景／视角／区间。
使用新的输出目录；保持原始媒体、描述文本和清单不变。

<a id="when-existing-per-view-captions-are-supplied"></a>
### 已提供各视角描述文本时

扩写时，将已有正文作为参考文本，而不是交通事实的判定依据。
保留兼容的明确外观与环境细节，必要时丰富它们，
并根据实际检查的 WSM 修正交通／运动或时间表述，同时保留四项必需属性。
将修正记录在 `NOTES.md` 中，而不是描述正文中。
WSM 无法判断同一参与者相互冲突的车漆颜色哪一个正确；
应依据明确的来源优先级作出选择，或询问用户要保留哪种外观；不能声称 WSM 已解决这一冲突。

编写新的文件包，不要覆盖原文件。
源文本的格式不自动决定输出格式：除非用户要求其他格式／长度，
或明确要求保留源格式，否则使用长篇带时间戳的描述文本。
已有描述文本不能替代 WSM 检查；
应请求缺失的控制或必需属性，而不是默默进行纯文本重写。
如果用户要求忽略原始描述文本，编写时完全排除它们。

编写时必须实际查看并检查 WSM。完成后的额外视觉复核是可选步骤，默认关闭，
不属于本生成指南的范围。

将任务限定于所请求的描述文本。
除非用户授权使用外部描述文本服务，否则将保密媒体留在本地。

<a id="1-establish-the-input-contract"></a>
## 1. 明确输入要求

先阅读用户输入；只询问会影响结果的缺失信息。记录：

| 输入 | 必需的解释方式 |
| --- | --- |
| 场景标识 | 区分不同变体；若存在 `(clip_id, video_uuid)`，使用该组合，而不只是共享的片段 ID。 |
| 四项属性 | 一天中的时段、天气／强度、道路材质／状况、地理环境；记录每个值及其用户／元数据来源。常见字段名为 `time_of_day`、`weather`、`road_surface`、`region`。 |
| 视角映射 | 明确相机键／方向到控制 URI／路径的映射及其来源；保留所选视角集合和键。 |
| 时间关系 | 请求区间、媒体时间戳／采样节奏、裁剪偏移和同步信息。不要假定标准片段长度。 |
| WSM 解读 | 适用的渲染器／图例，或关于类别、信号、线条和任何轨迹 ID 的经验证约定。 |
| 文本 | 若作为扩写源文本提供，则记录已有各视角正文及其格式。 |
| 输出 | 所需格式、长度和保存位置。除非明确指定其他要求，否则默认使用长篇带时间戳描述文本，每个所提供视角的正文合计 300–400 个词。 |

不要从 WSM 类别颜色或黑色背景猜测四项属性。
若某项属性缺失，请求该属性或权威来源。
经用户确认不作限定的属性，可以保持未指定状态；
对应检查项应标记为“未指定”，而不是“通过”。
`keepOriginal` 需要有依据的原始环境；该标记本身并不能识别地理环境。

新的用户指令可以明确替换元数据属性；记录该覆盖。
若来源冲突且没有清晰优先级，应询问，而不是默默选择更容易处理的设置。
已有叙述不能隐式覆盖这四项属性，也不自动构成必须发生的交通事件要求。

编写描述文本前，检查缺失／重复键、可疑映射和时间不一致。
依据标定与渲染视图验证相机方向，并使用源时间戳检查同步。
在按相机视角描述方向之前，先解决映射冲突。

如果缺少控制、映射、渲染器语义或图像查看能力，
执行有依据的文本／属性检查，并报告具体证据缺口。
不要声称这些描述已经过 WSM 核验，也不要擅自改为不检查图像的纯文本生成。
对于语义不明的要素，应暂缓相关判断；不受影响的观测仍可记录。

<a id="2-inspect-synchronized-wsm-evidence"></a>
## 2. 检查同步 WSM 证据

1. 探测所选控制的尺寸、帧数、FPS／PTS、时长、偏移和解码错误。
   将所选区间统一到以该样本起点为零的时间轴上。
   对于均匀采样节奏，`N / FPS` 是半开区间时长；
   `(N - 1) / FPS` 是最后一帧的时间戳。
   未确认语义前，切勿从名称含糊的字段推导裁剪偏移。
2. 解码并**查看**覆盖所选区间的概览，包括所有所选视角的开头和结尾。
   约八个同步时间戳是有用的起点。
   标注相机键、帧索引和实际时间戳。缩略图拼图中的细节必须清晰可辨。
3. 建立共享的初步交通清单。
   对重要问题请求额外相邻帧和全分辨率裁剪：
   边缘部分入画、出画、遮挡与检测器漏检的区别、小型参与者／信号、
   同时出现的检测结果，以及不确定的跨视角物体对应关系。
   明确每个请求要回答的问题。不要根据缩略图推断小物体不存在。
4. 保留紧凑的证据记录，将观测关联到视角／时间／帧文件。
   区分“已保存到磁盘的帧文件”和“实际查看过或已提供给编写 API 的图像内容”。
   只有后者才能声称经过视觉验证。

使用可用的图像查看工具检查解码帧。仅解码不等于检查。
在此工作流中，不要用参考／生成 RGB 替代 WSM 证据。
如果用户需要以 RGB 为条件的描述文本，应明确它属于不同范围，
而不是擅自改变判定事实的依据。

按源文件标识／内容摘要及帧号／时间建立缓存，而不是仅使用不含目录的文件名。
恢复工作时，保留证据记录，复用前验证缓存图像，
并重新向描述文本编写者发送相关概览／细节帧。保持原始控制不变。

将额外检查限制在重要论断上。
如果时间或预算耗尽后仍存在影响结论的不确定性，应明确报告，不得将结果标记为已通过验证；
不要为迁就预算而删除参与者、放宽请求属性或声称已经验证。

<a id="3-establish-one-scene-then-generate"></a>
## 3. 建立一个统一场景，然后生成

将工作记录分为：

- **必需环境属性：** 四项属性、各自来源，以及用户明确指定的覆盖值。
- **WSM 观测：** 按相机／时间记录物体／类别、几何、位置和可见性，
  有依据的运动／信号，以及未解决的关联。
- **外观：** 保留的源属性，或新指定的合理车漆、玻璃、材质与纹理。
  指定外观并不是从 WSM 恢复的真值。

对每个已充分辨明的物体／地标只指定一次外观，并在不同视角与时间中复用。
不要将尚未厘清关系的检测结果强行认定为不同物体。
将对原始叙述的修正说明与提示词正文分开记录。

根据这份共享记录，按请求格式编写文本。
每段正文只描述对应相机在该时间区间内能看到的内容。
在语义上保留全部四项属性，不要强迫每个视角都出现海、天空或其他画外地标。
使用具体且与场景相容的外观描述，不要堆砌质量口号或无意义的填充语句。

带时间戳的描述使用经核验的片段内时间边界，例如 `[0.0s-3.5s]:`；
段落描述不需要时间戳。
将跟踪 ID、证据、不确定性讨论和跨相机标注说明排除在生成正文之外。
不要仅为填满区间而添加事件脚本。

默认在编写完成并通过下述低成本一致性／格式检查后结束；
记录 `visual_review: not_run`。
不要仅因已生成描述文本，就重新查看证据、启动审阅代理或进入审阅／修订循环。

<a id="4-validate-and-hand-off"></a>
## 4. 验证与交付

始终依据已检查的证据和共享记录，联合核对各视角文本中的外观、
四项属性、自车运动及事件发生时间是否一致。
编写时核对交通描述及物体在对应相机中的可见性；
必要时用相邻观测界定所叙述的入画／出画，包括部分可见情况。
这些检查不需要单独的视觉审阅阶段。
保留不会影响有依据描述的不确定性，
但不要隐藏会使其中某个论断失效的不确定性。

通过程序化检查确认视角键集合是否准确、格式和长度是否符合要求，
以及存在时间戳时其边界的有效性与顺序。
跨视角正文边界可以不同；若请求 sidecar，外层 sidecar 帧跨度必须一致。

默认在新的本地输出目录中交付：

- `captions.json`：相机键到正文的映射，不是可执行推理请求。
- `NOTES.md`：输入／属性来源、共享外观、检查过的证据、
  检查项、来源修正和未解决问题。

对于已经完成编写但未额外审阅的结果，记录 `status: generated`
和 `visual_review: not_run`。
未完成工作使用 `draft`，并在 `NOTES.md` 中记录未解决项。

仅在请求时打包 sidecar／清单。
保留非描述文本元数据、控制、初始图像和设置；不要重复相机组／相机头部。
在确认文件包可用于推理之前，检查目标读取器及其实际解析出的各视角文本。
不要假定顶层场景提示词就是每台相机实际读取的文本，
也不要擅自将它复制到侧视或后视相机。

<a id="caption-policy"></a>
## 描述文本策略

生成描述文本或扩写已有文本时应用本策略。
结合所有相机理解同一个物理场景，再分别从各相机视角编写正文。

<a id="source-authority"></a>
### 来源的权威范围

| 来源 | 可以确定什么 | 不能确定什么 |
| --- | --- | --- |
| 用户／场景元数据 | 要求的时段、天气、路面状况和地理环境；另行明确指定的必需事件 | 特定视角中的交通可见性或物体轨迹 |
| 已检查的 WSM 加经验证的渲染器约定 | 已检查时刻有依据的交通物体／类别、几何、可见性、信号和运动 | 真实车漆、品牌／型号、地理环境、光度照明或天气 |
| 兼容的原始叙述 | 值得保留的预期外观／背景细节 | 权威交通事件，或对明确场景属性的覆盖 |
| 指定的外观 | 与上述内容一致的合理具体外观 | 声称 WSM 恢复了真实外观 |

当源叙述与 WSM 交通证据矛盾时，应修正源叙述。
在备注中记录 `Source correction`，而不是写入描述正文。
例如，如果所选 WSM 区间只显示车辆正在接近，
就不能因为原始叙述写了“等待绿灯”而把它描述为停车，也不要编造之后起步离开的情节。
只有用户另行明确要求某事件必须发生时，该事件与控制数据的冲突才构成需要先解决的输入问题。
不要从文件名、数据集标题或重复叙述中推断强制事件。

WSM 是描述文本编写的参考，不是绝对无误的物理真值。
检测中断不能证明物体消失。
两个同时出现的长方体只能说明画面渲染了两个检测结果，不一定对应两辆真实车辆；
上游可能存在重复检测。检查相邻证据，保留未解决解释，避免没有依据的计数。
不要为了修补看似存在的感知遗漏而编造参与者。

<a id="traffic-camera-locality-and-identity"></a>
### 交通、逐相机可见性与物体身份

- 不要添加缺乏依据的车辆、行人、骑行者、交通标志／标志文字、
  信号、车道标线、人行横道或交通几何。
  保留有依据的类别和粗略形状；长方体不是品牌或精确子类型的证据。
- 解读颜色、信号或类别标签前，先验证图例。
  类别颜色不是车漆，相同颜色也不是物体 ID。
  未知类别应保持未知，不要擅自将其认定为行人或某类设备。
- 每个数量和位置都要限定相机与时间。
  整个片段的清单不是同一帧的同时计数。
  避免无依据的“全部”“唯一”“始终”、精确速度／距离或精确独立物体总数。
- 区分图像中的左／右、自车的左／右，以及相对于道路的车道位置和行驶动作。
  即使物体没有改变行进方向，屏幕运动在不同相机中也可能相反。
  同一时刻不能既把自车描述为静止，又描述为正在行驶。
- 不同相机可能看到控制不同驶入方向的信号；
  不要假定每个可见信号灯都控制自车车道。
- 使用连续性、几何、尺寸、重叠，以及可用且经验证的轨迹 ID 关联物体。
  为检查临时分配的标签只是注释，不是恢复出的真实轨迹 ID。
  明确保留不确定关联，而不是编造身份确定性。
- 保留兼容的已提供外观；否则，只指定一次合理的车漆、玻璃、
  表面处理或服装，并在可见视角／时间之间共享。
  不要让同一物体在不同视角中变色、重复添加同一地标，
  也不要先给模糊检测分配不同颜色，再据此声称它们是不同物体。
- 仅在与受控制几何和请求环境兼容时，合成非交通的表面／背景细节。
  不要用新结构堵塞车道、改变道路拓扑，或在每个视角放置一个编造的地标。
- 不要把前向驾驶叙述粘贴到侧／后视角。
  共享天气和物理身份不要求相同正文或相同屏幕空间位置。
  在编写备注中解释跨视角关联，而不是写进模型提示词。

<a id="four-properties-meaning-not-keyword-presence"></a>
### 四项属性：检查含义，而不是关键词是否出现

读取精确选定场景的属性值。不要借用同一片段的另一个天气变体的值。
规范化字段名时，不要丢失其语义。

| 属性 | 检查内容 | 冲突或过度推断示例 |
| --- | --- | --- |
| 一天中的时段 | 天空、阴影和照明与请求时段一致 | “夜间”却有阳光照射的立面或日间蓝天 |
| 天气 | 类别与强度保持可辨认；可见度与之相符 | “浓雾”却有完全清晰的远景；将大雪替换为几片雪花 |
| 路面状况 | 保留指定材质与状况 | 将 `wetConcrete` 描述为干燥沥青；将 `damaged` 改写为完好无损路面 |
| 地理环境 | 环境兼容，但不强行加入看不见的地标 | 将 `coastal` 解释为每台相机都能看到海；根据 `keepOriginal` 编造国家 |

每段正文应在适用处自然传达所请求的环境，并与全部四项属性兼容。
它们是共享条件，不要求每个视角都显示相同证据。
看不到海的后视画面仍可以处于沿海。沙漠道路不一定是沙地。
`keepOriginal` 要求明确原始环境，或明确标注未解决的限制。

保留用户指定的属性组合，不要擅自改成常见搭配：
有雾不意味着路面一定潮湿，有降雪也不意味着可以覆盖“干燥沥青”的明确要求，
`slippery` 本身也不意味着结冰。
标记真正不可调和的要求，而不是默默替换其中一个。
不要依据 WSM 背景决定天气。

白天并不意味着交通信号灯或车辆行车灯关闭。
反之，不要编造灯柱或其他交通基础设施来解释夜间照明。
不同朝向的相机可以看到不同的反射和亮度，但不应因此改变太阳位置、天气或已设定的车漆颜色。

<a id="atmospheric-weather-versus-optical-blur"></a>
#### 大气天气与光学模糊

保留雨、雾、雪和夜间条件；不要为了保证清晰而删除它们。
镜头清洁、无遮挡，并不意味着场景中不能有雾或雨。
除非请求，否则避免添加固定在相机上的油污、冷凝水、附着水滴或全画面涂抹。
如果明确要求镜头污染，应保留，而不是用“干净镜头”模板覆盖。

通过随深度变化的衰减描述雾，按请求强度描述雨／雪，
近处细节也只能描述到可见度允许的程度。
不要编造可见距离，也不要保证所有距离都清晰。
路面反射、飞溅以及积水或积雪也必须符合路面状况要求。
不要为了说明画面为何清晰而编造挡风玻璃、雨刷或交通参与者。
光学相关条款应简短；它不能替代具体场景外观，也不是经证实能修复生成伪影的方法。

<a id="time-visibility-and-prose"></a>
### 时间、可见性与叙述

使用统一的片段内时间轴，但不要求各相机的描述段落采用完全相同的时间边界。
检查所叙述变化前后的画面，而不是从稀疏概览推断精确时间。
物体即使只在画面边缘露出很小一部分，也仍算可见。
区分首次部分可见与变得显著，也要区分离开 FOV 与遮挡／检测中断。

例如，如果物体在 3.2667s 时位于被裁切的边缘，在 3.3000s 时已不可见，
那么从 3.5s 开始的描述应说它“已经离开边缘”，而不是说它在该区间中“离开”。
如果物体在区间开始时就已被边缘裁切，应描述该初始状态。

带时间戳的叙述应使用实际选择的边界，并划分足够区间来表达有意义的变化，
而不是随意均分。在段落叙述中，区分先后出现与同时出现；
限定随时间变化的位置／信号，而不是将它们冻结在整个片段中。
没有描述运动，不等于可以把所有物体写成静止状态。

具体外观优于关于自然色彩、透视、图像质量或可见细节的泛泛填充。
不要为满足长度而添加声音、意图、安全判断、车牌、品牌或装饰性标志文字。
如果所请求长度需要缺乏依据的论断或重复才能达到，应报告限制，而不是凑字数。
将相机／相机组头部与正文分开。
